## Request

`docs/completion.md` asks for a completion-script generator whose public API looks like:

```zig
CLI.completion(arena, .zsh); // returns []const u8
```

for `zsh`, `bash` and `fish`, with no view argument.

The no-view instinct is correct. Completion is a pure function of the comptime declaration: the normalized `specs` and
`commands` tables plus `app_meta`. A `View` only carries runtime values, and no runtime value can change which flags or
commands exist. It is the same data `helpData` and `helpText` walk, so no parse and no `View` is needed.

One correction to the sketch: building the script allocates, so the function must be fallible unless it is generated
entirely at compile time. This is U2.

## Architecture: static or dynamic

Two architectures are possible and they must be chosen before the rest of the plan.

**Static (proposed).** The generated script embeds the whole declaration: each command level's flags, subcommands and
(optionally) enumeration values. The script scans the words before the cursor, tracks which command level the user is
on, and prints that level's candidates. No runtime callback, no change to the user's `main`, no new parse path. The
script is a snapshot: if the binary's declaration changes, regenerate it.

**Dynamic.** The script calls the binary to obtain candidates, typically by shipping `_DAP_COMPLETE=zsh` in the
environment (or a hidden token) and having the user intercept it before `parse`. That would add a second public API
returning runtime candidates from raw argv, plus a documented hook in every user `main`; it buys exact values, i18n and
custom-provider data, but it is a much larger surface. It also does not remove the need for a small shell adapter per
shell.

The rest of this letter assumes static. That assumption is the blocking U1.

## What the generated namespace already provides

- `generate` builds a local `Base` with `app_meta`, `specs`, `commands` and `View`, then returns it verbatim for a
  commandless level or a forwarding shell for a level with commands (`src/dap.zig:2001`, `src/dap.zig:2125`,
  `src/dap.zig:2759`).
- `specs` is the flat normalized list: the injected `-h, --help` is first, group and `Alt` members are already
  flattened, and every entry carries `kind`, `long`, `short`, `vtype`, `optional`, `alt` and `help`
  (`src/dap.zig:2916`). For a flag, `long` is always the wire name. For an `Enumeration` value type, `vtype.names` is
  the wire-name list (`src/dap.zig:358`).
- `commands` carries one `CommandEntry` per child: declaration `field`, wire `name`, pre-order `rank` and the
  `Command(...)` type `Cmd` (`src/dap.zig:2954`). `Cmd.cmd_meta.help` is the child's description.
- `Sub(c.Cmd, subApp(app, c))` is the child namespace, and `commandNodes` already rebuilds the entire tree by type
  (`src/dap.zig:2814`, `src/dap.zig:2857`, `src/dap.zig:2904`).
- Parsing retries an unknown flag against every ancestor level (`src/dap.zig:2555`, `src/dap.zig:2602`), so a deep
  command accepts ancestor flags. Flag long names and short aliases are globally unique across the whole tree
  (`collectFlagOrigins` / `checkGlobalFlagNames`), which a generated scanner may rely on.
- Short aliases are whole tokens: `assignShortFlag` matches the whole body, so `-abc` means the short alias `abc`, not
  `-a -b -c` (`src/dap.zig:3186`). Both long and short forms accept `=value`.
- Boolean flags never consume the next token; every other value type does (`src/dap.zig:3154`, `src/dap.zig:3186`). This
  is the same `takes_value` rule help uses (`src/dap.zig:2358`).
- `Alt` members are ordinary flags with an `alt`/`alt_branch` tag; all branches are accepted at the start, and conflicts
  are detected during parsing.

## Public surface

### Proposed API

```zig
/// Shell dialect a completion script is generated for.
pub const CompletionShell = enum { bash, zsh, fish };
```

In `Base`, beside `helpData`/`helpText`:

```zig
pub fn completion(
    allocator: std.mem.Allocator,
    shell: CompletionShell,
) std.mem.Allocator.Error!String
```

- `String` is the project alias for `[]const u8`.
- Returns one complete script, terminated by one newline, so redirecting it to a file or piping it is clean.
- The caller owns the result through `allocator`; with an arena, the arena releases it. There is no hidden cache and no
  internal free function.
- The only failure is `OutOfMemory`.
- Output is deterministic: the same declaration and shell produce identical bytes, with no timestamps or environment
  probes.
- The generated shell forwards it: `pub const completion = Base.completion;` in the command accessor shell
  (`src/dap.zig:2759`). A commandless level has it directly, because `generate` returns `Base`.
- `src/root.zig` re-exports `CompletionShell`; the function itself is reached through the generated namespace, like
  `parse` and `helpText`.

Call shape:

```zig
var arena = std.heap.ArenaAllocator.init(std.heap.page_allocator);
defer arena.deinit();
const script = try CLI.completion(arena.allocator(), .zsh);
```

The doc's `CLI.completion(arena, .zsh)` becomes `try CLI.completion(...)` unless compile-time generation is chosen; the
first argument is a `std.mem.Allocator`, matching `helpData`, `helpText` and `parse`.

### Why runtime allocation

Generating the three scripts entirely at comptime and returning a static literal would make the function infallible, but
it requires either all three scripts to be materialized (binary bloat even when one is unused) or a comptime-known shell
argument. Building large strings at comptime is also quota-heavy. Runtime generation into the caller's allocator is how
`helpData`/`helpText` already work and scales to large trees. U2 asks to confirm.

### Root-only scope

The script is tied to a binary's argv, not to a parsed value. A subcommand level cannot reconstruct its ancestors from
`app_meta.name` alone: the name is a space-joined path, command names may themselves contain spaces, and there is no
parent pointer. Since parsing accepts ancestor flags at every level, a "subtree only" script would advertise an
incomplete flag set.

Proposal: `completion` exists on every generated namespace, but a call on a non-root level is a `@compileError`:

```zig
comptime {
    if (app._command_rank != 0)
        @compileError("dap.completion: call it on the root namespace");
}
```

Only the root output is installable. U3 asks to confirm, or to define a subtree-only contract.

## Level model

Completion needs something `commandNodes` does not preserve: ancestry. A level's effective flags are its own flags plus
every ancestor's flags, because the parser resolves ancestor flags after a handoff. Commands and arguments, by contrast,
belong to the current level only (the parser rejects mixing them, so an argument-bearing level is a leaf).

A private comptime table drives all three emitters:

```zig
const CompletionLevel = struct {
    rank: usize,                      // App._command_rank, unique in the tree
    path: String,                     // App.name, for script comments
    flags: []const Spec,              // ancestors first, then own; builtin once
    arguments: []const Spec,          // own only
    commands: []const CommandEntry,   // own only
};

fn completionLevels(
    comptime NS: type,
    comptime inherited_flags: []const Spec,
) []const CompletionLevel {
    comptime {
        var flags = inherited_flags;
        for (NS.specs) |s| {
            if (s.kind != .flag) continue;
            var dup = false;
            for (flags) |prev| {
                if (std.mem.eql(u8, prev.long, s.long)) dup = true;
            }
            if (!dup) flags = flags ++ &[_]Spec{s};
        }

        var args: []const Spec = &.{};
        for (NS.specs) |s| if (s.kind == .argument) {
            args = args ++ &[_]Spec{s};
        };

        var out: []const CompletionLevel = &[_]CompletionLevel{.{
            .rank = NS.app_meta._command_rank,
            .path = NS.app_meta.name,
            .flags = flags,
            .arguments = args,
            .commands = NS.commands,
        }};
        for (NS.commands) |c| {
            out = out ++ completionLevels(
                Sub(c.Cmd, subApp(NS.app_meta, c)),
                flags,
            );
        }
        return out;
    }
}
```

The root call is `completionLevels(@This(), &.{})`. The recursion uses the same `Sub(c.Cmd, subApp(...))` expression as
`View` and `CommandPayload`, so it is the identical namespace instantiation. The builtin help flag is the only
intentional duplicate across levels; deduplicating by `long` keeps exactly one `-h, --help` per effective set. Global
uniqueness makes the check exact.

The table is pre-order, root first, matching `commandNodes`. Emitters should iterate it with `inline for` so `s.vtype`
remains comptime-readable for enumeration detection. `@setEvalBranchQuota(1_000_000)` at the entry point matches
`generate`.

## Context resolution

All three emitters implement the same scan. It is the normative algorithm; each shell is a translation of it.

Given the shell's words, with `argv[0]` and the current (partial) word excluded:

1. Start at level rank 0, `literal = false`.
2. For each previous word:
   - if `literal`, ignore it;
   - if the word is exactly `--`, set `literal = true`;
   - if the word is exactly a value-taking flag (a flag whose `vtype != bool`), skip the next word, which is that flag's
     value;
   - if the word has the form `--long=value` or `-s=value`, do not skip;
   - if the word starts with `-` and has length greater than 1, it is a flag, so do not consider it a command;
   - otherwise match it against the current level's command names; on a match, descend to that command's level.
3. Resolve completion for the current word against the final level.

Value skipping is not cosmetic. In `app --file run`, `run` is the value of `--file`, not a subcommand; a scanner that
ignored this would offer the `run` level. The parser behaves the same way: `assignLongFlag` consumes the next argument
for every non-boolean flag (`src/dap.zig:3154`).

The skip table may be global (every value-taking flag in the tree) because long and short names are globally unique. The
candidate table must be per-level, because sibling flags are not valid after a handoff.

After `--`, the parser treats the rest as literal positionals and suppresses handoff (`src/dap.zig:2580`). The scanner
sets `literal` and offers no flag/command candidates in v1; the shell's default file completion remains.

## Candidates

At the resolved level, for an ordinary (non-value) current word, offer:

- every effective flag, in declaration order (ancestor flags first, builtin help at the root's position), as two
  candidates when a short alias exists: `--long` and `-short`;
- every command of the level, as `c.name`, in declaration order.

Descriptions are attached per shell in U5.

Value positions:

- if the previous word is exactly a value-taking effective flag, offer the enumeration values of its `vtype`, bare, when
  `vtype` is an `Enumeration(...)` result; otherwise offer nothing and let the shell's file completion apply;
- if the current word starts with `--long=` or `-short=` for a value-taking effective flag, offer full `--long=value` /
  `-short=value` candidates for an enumeration; otherwise offer nothing;
- after `--`, offer nothing in v1.

Directional details:

- `Enumeration` detection is structural: `@hasDecl(vtype, "EnumView")` and `@hasDecl(vtype, "names")`, then use
  `vtype.names`. The empty `Enumeration` result has no `names` and yields no candidates.
- Boolean flags never enter a value position, even though `--flag=true` is accepted.
- `Alt` branches are not pruned after one branch activates. The parser reports the conflict; completion may keep
  offering both, which keeps the generator simpler and avoids tracking union state in shell code.
- Argument values are not completed in v1. Shell file completion is the default for leaf levels, which is usually right
  for path arguments. U4 asks whether to include enumeration-typed arguments and their slot tracking.

Candidate names are the exact wire spellings: no case folding, no removal of a leading dash, no normalization. Empty
long or short spellings are skipped: an empty long flag can never be written (`--` is the terminator) and an empty
candidate is not representable in any of the three shells. Empty command names are skipped for the same reason. Command
names that start with `-` are unreachable by the parser (flag matching runs first) and would be misleading; the
implementation may filter them or document the limitation.

## Descriptions and i18n

The data is already present: `Spec.help` for flags, `cmd_meta.help` for commands. `i18n` references are inert everywhere
else, including the compact help renderer, so completion should not invent a translation path.

Proposal: zsh and fish show the raw help string as the candidate description; bash has no description UI and emits only
words. Descriptions are sanitized (newlines, carriage returns and tabs become spaces) before quoting. U5 asks whether to
include them at all.

`Enumeration` currently discards each branch's `Enum.help`; value descriptions would require exposing a parallel `helps`
table on the `Enumeration` result. Proposal for v1: enumeration values appear without descriptions.

## Emitters

U6 covers the emitter strategy. The proposal is one dependency-free, scan-based function per shell with per-level data
tables. The alternative is idiomatic shell machinery (`_arguments -C` in zsh, `complete -n` conditions in fish,
`_init_completion` in bash), which behaves more natively but is harder to generate correctly for arbitrary nested trees.

All user strings are data, never shell syntax. Function and variable identifiers are derived from a sanitized binary
name, not from arbitrary command names, so command names with `-`, spaces or punctuation cannot break the script. All
literals are quoted by a per-shell helper.

### bash

Target bash 3.2+ (macOS default): arrays, `[[ ]]`, `local`, arithmetic loops; no associative arrays, `mapfile`, or
`compopt`.

- One driver `_dap_<ident>`; per-level candidate arrays `_dap_<ident>_cand_<rank>` and per-level value arrays.
- Registration: `complete -o default -F _dap_<ident> <bin>`.
- `-o default` keeps filename completion for positions v1 does not handle.
- Filter with an array loop rather than `compgen -W`, because `-W` word-splits candidates and would break command names
  containing spaces:

```bash
_dap_myapp_filter() {
    local cur=$1; shift
    COMPREPLY=()
    local c
    for c in "$@"; do
        [[ $c == "$cur"* ]] && COMPREPLY+=("$c")
    done
}
```

- The driver sets `cur`/`prev` from `COMP_WORDS`/`COMP_CWORD`, runs the scan, then dispatches:

```bash
case "$level" in
    0)
        case "$prev" in
            '--color'|'-c') _dap_myapp_filter "$cur" "${_dap_myapp_vals_0_color[@]}"; return ;;
            '--file'|'-f') COMPREPLY=(); return ;;
        esac
        case "$cur" in
            '--color='*) _dap_myapp_filter "$cur" "${_dap_myapp_eq_0_color[@]}"; return ;;
        esac
        _dap_myapp_filter "$cur" "${_dap_myapp_cand_0[@]}"
        ;;
    1) # ... same shape for the child level
        ;;
esac
```

- The scan's command dispatch is nested per level, for example `0) case "$tok" in 'run') level=1 ;; esac ;;`, so command
  tokens are always compared as literal strings.
- Short aliases are matched whole; no cluster expansion.
- Descriptions are not emitted.

### zsh

Target zsh 5.x. The output should work both as an autoload file named `_<bin>` and when sourced from a process
substitution.

- First line `#compdef <bin>`.
- Root driver function `_<bin>` (the autoload function name). Variables are `local`; candidate arrays are filled per
  level by the dispatcher.
- Standard self-registration guard:

```zsh
#compdef myapp
_myapp() {
    # scan words[2..CURRENT-1], then:
    local -a cands displays
    case $level in
        0) cands=('--help' '-h' '--run'); displays=('--help  Show help.' ...) ;;
    esac
    (( ${#cands} )) && compadd -o nosort -d displays -- "${cands[@]}"
}
if [ "$funcstack[1]" = "_myapp" ]; then
    _myapp "$@"
else
    compdef _myapp myapp
fi
```

- `compadd` filters by `PREFIX`, so full `--flag=value` candidates work without a `compset` dance: the current word
  `--color=r` filters `--color=red`.
- `compadd -d` takes a parallel display array, avoiding `_describe`'s colon-separated format and the need to escape `:`
  inside names or help. Verify this option during implementation; `_describe` is the fallback.
- For a value position after `--color`, emit bare enumeration values.
- For a non-enum value flag, emit nothing; zsh's default completion handles files.
- After `--`, return without adding matches.

### fish

Target fish 3.x.

- One function `__dap_<ident>_complete`.
- Previous words: `set -l toks (commandline -opc)`. It already excludes the current token, partial or empty (verified on
  fish 4.2: with `daptest --color r`, `-opc` yields `daptest --color` and `-ct` yields `r`). Drop `toks[1]` (the
  binary). `commandline -ct` is needed only for `cur`, to pick the value form (`--color=...`) and test the `--`/value
  positions; fish itself filters the printed candidates.
- Run the same scan in fish syntax; use `string match -q -- '--color=*' $cur` for prefix tests, because quoting a `*` in
  a fish `case` pattern makes it literal.
- Dispatch and print per level:

```fish
switch $level
    case 0
        printf '%s\t%s\n' '--help' 'Show context-sensitive help.'
        printf '%s\t%s\n' '-h' 'Show context-sensitive help.'
        printf '%s\n' 'run'
end
```

- Registration: `complete -c <bin> -a '(__dap_<ident>_complete)'`.
- No `-f`: file completion stays available for arguments and non-enum values. The function prints nothing in those
  positions, so fish falls back to files.
- Tab separates candidate from description in the command-substitution output. Sanitize tabs and newlines in
  descriptions and values; a newline in a candidate cannot be represented by this protocol and is a documented
  limitation.

### Installation

The library only returns the script; the user wires the printing command in their own `main` (for example, a normal
`completion` subcommand). Document:

```sh
app completion bash > /etc/bash_completion.d/app
app completion zsh  > "${fpath[1]}/_app"
app completion fish > ~/.config/fish/completions/app.fish
```

For zsh, the `funcstack` guard also makes `source <(app completion zsh)` work. For bash, the trailing `complete` line is
enough. For fish, dropping the file into the completions directory is enough.

U7 covers the version floors, the bare binary-name requirement, and whether one install mode per shell is sufficient.

## Failure, size, determinism

- Only `OutOfMemory`. The emitter writes into one `std.ArrayList(u8)`; `errdefer out.deinit(allocator)` guarantees no
  partial buffer survives an allocation failure. No partial script is returned.
- There is no caching. Each call rebuilds the script; with an arena, repeated calls accumulate.
- Size is linear in the tree. Effective flag lists duplicate ancestors in each descendant's table, so a deep tree
  repeats flag names at each level. That is intentional: the alternative is runtime ancestor lookups in shell code,
  which is harder to keep correct.
- No `View`, no parse, no environment, no file I/O, no locale or translated text.

## Placement and ordering

Following the file's existing order (`src/dap.zig`):

1. `CompletionShell` goes with the public data types near `Kind` and the help renderer types.
2. Private scaffolding goes before `generate`, beside the help scaffolding: `CompletionLevel`, `completionLevels`,
   `completionScript`, the three emitters, shell quoting/sanitizing helpers, the enumeration detector, and the
   effective-flag merge.
3. `Base.completion` goes beside `helpData`, `helpText` and `usage`; the command shell forwards it in the alias block
   (`src/dap.zig:2759`).
4. `src/root.zig` re-exports `CompletionShell`.
5. `README.md` gains a `## Completion` section after `## Help`, with the API and installation commands. `AGENTS.md`

6. No DSL or declaration syntax changes; no `View` layout changes; no parser changes; no normalization changes.

`src/main.zig` should gain a small `completion` command in the example tree so the generated scripts can be checked

## Tests

A new `M19` block in `src/dap.zig`, matching the existing milestone style.

Pure Zig tests, with `std.testing.allocator`:

- A minimal tree (one bool flag, one enumeration flag, one command, one nested command) and a larger tree with `Group`,
  `Alt`, optional flags and an argument-bearing leaf.
- Per-level candidate assertions: root flags and commands; child sees ancestor flags plus its own and its own commands;
  sibling flags never leak; the builtin help appears exactly once per effective set.
- Enumeration values: bare after `--color`, full `--color=red` after `--color=`, `-c=red` after `-c=`, absent for
  non-enum value flags.
- Value-skip fragments: every non-bool flag is in the skip table, bool flags are not; `--color=red` is not a skip form;
  `--` is emitted as a stop.
- `--` handling: no flag or command candidates after the terminator.
- Quoting: help and command names containing `'`, `"`, `\`, spaces and `:` produce the right shell-specific escaping;
  function identifiers never contain user text.
- Determinism: two calls produce identical bytes.
- OOM sweep with `std.testing.FailingAllocator`, in the style of
  `M9: helpData frees everything when an allocation fails` (`src/dap.zig:5354`), asserting
  `allocated_bytes == freed_bytes` for every `fail_index`.
- Full golden scripts for a tiny tree, one per shell, to lock registration, the zsh guard, the fish registration line
  and the overall skeleton. The larger tree is asserted structurally so it does not become brittle.

No external shell is required for `zig build test`. Optional integration checks:

```sh
app completion bash | bash -n
app completion zsh  | zsh -n
app completion fish | fish -n
```

Semantic checks are possible but asymmetric: bash can be fed `COMP_WORDS`/`COMP_CWORD` and inspected through
`COMPREPLY`; fish can use `complete -C 'app r'`; zsh needs a real completion context. U8 asks whether these should be
mandatory when the shell is installed, or remain a manual check.

## Non-goals for v1

- Dynamic runtime callbacks or user-provided value providers.
- Completing custom value types (only `Enumeration` is enumerable).
- Positional-argument value completion and precise file filtering.
- Pruning `Alt` branches after activation.
- Resolving `i18n` references.
- Aliases, renamed binaries, or symlinked invocation names.
- PowerShell, nu, elvish, or other shells.
- Using zsh `_arguments` or bash-completion's `_init_completion`.

## Risks to verify during implementation

- `compadd -d` display semantics and `PREFIX` filtering in zsh; the `funcstack` guard in both autoload and sourced
  modes.
- fish `commandline -opc`/`-ct` behavior at the cursor, and whether tab-separated output reliably carries descriptions
  for `complete -a`.
- bash 3.2 compatibility; `compopt` is unavailable, so per-call disabling of default file fallback is not possible.
- Candidate names containing spaces (handled by arrays/compadd/fish lines), colons (why `compadd -d` is preferred over
  `_describe`), and newlines (not representable in fish's line protocol).
- Root `App.name` containing whitespace or `/`; it breaks registration and zsh function naming. Proposal: compile-error
  on a non-bare root name.
- Sanitized identifier collisions (`a-b` and `a_b` both become `a_b`) when two dap CLIs are sourced into the same
  bash/fish session; zsh is naturally namespaced by `_<bin>`.
- `App._command_rank` is documented internal but is a public struct field; a user-supplied value could defeat the
  root-only check. Not worth defending beyond the compile message.
- Large trees: compile-time table construction and the size of the emitted script; no laziness is planned.

## Open questions

- **U1 (blocking).** Static or dynamic completion? Proposed: static. The script embeds the declaration and scans the
  words itself, so there is no runtime protocol, no change to the user's `main`, and no second API. Dynamic would add a
  `complete(raw_args, shell)` helper plus an environment handshake before `parse`; it is more exact for values and i18n,
  but much larger. This choice determines everything below.

- **U2 (blocking).** Exact signature and ownership. Proposed:

  ```zig
  pub const CompletionShell = enum { bash, zsh, fish };
  pub fn completion(
      allocator: std.mem.Allocator,
      shell: CompletionShell,
  ) std.mem.Allocator.Error!String;
  ```

  The doc's `CLI.completion(arena, .zsh)` becomes `try CLI.completion(arena.allocator(), .zsh)`; an arena releases the
  result. The alternative is a comptime-generated static `[]const u8` with no error union, at the cost of binary size
  and comptime quotas. Confirm the runtime allocator plus error union and the `CompletionShell` name.

- **U3.** Should `completion` be callable on a subcommand namespace? Proposed: root only, with a `@compileError` on a
  non-root level. A child cannot recover ancestor flags from `app_meta.name` (names may contain spaces, and there is no
  parent pointer), while parsing accepts ancestor flags, so a subtree script would be incomplete. The alternative is to
  allow it as "subtree only" and document the missing ancestors, or to thread ancestor metadata into `App`.

- **U4.** What does v1 complete? Proposed: flags (long and short), commands, and enumeration values for flag value
  positions; no positional argument values, no custom-type values, no `Alt` pruning, and no file filtering beyond the
  shell default. If enumeration values are included, they have no descriptions unless `Enumeration` grows a `helps`
  table, because the current result type keeps only `names`. Confirm the scope, and whether enumeration-typed positional
  arguments matter in v1.

- **U5.** Descriptions. Proposed: zsh and fish show `Spec.help` / `cmd_meta.help` as the candidate description; bash
  shows none; `i18n` stays inert, as in the help renderer. The alternative is no descriptions at all (smaller scripts,
  less sanitizing) or a user hook for i18n (out of scope).

- **U6.** Emitter strategy. Proposed: a uniform, dependency-free scan-based resolver replicated per shell, with
  per-level candidate tables. This avoids bash-completion's `_init_completion`, zsh's `_arguments` state machine, and
  fish's `__fish_seen_subcommand_from` ambiguity when the same command name appears in different branches. The
  alternative is idiomatic per-shell constructs, which behave more natively but are much harder to generate and
  version-proof. Confirm the scan-based design or choose idiomatic emitters.

- **U7.** Installation and version contract. Proposed: bash 3.2+ (arrays, no `compopt`, no associative arrays), zsh 5.x
  (`#compdef`, `compadd -d`, `funcstack` guard so one artifact works autoloaded and sourced), fish 3.x
  (`commandline -opc`/`-ct`, `complete -a`). The root `App.name` must be a bare command name, non-empty with no
  whitespace or `/`; `completion` compile-errors otherwise. Identifiers are namespaced from the sanitized binary name so
  several dap CLIs can coexist. Are these floors and constraints acceptable, and is one install mode per shell enough?

- **U8.** Verification. Proposed: pure Zig goldens and structural tests, including an OOM sweep, with no shell execution
  in `zig build test`; optional manual `bash -n` / `zsh -n` / `fish -n` and semantic checks. Should CI or
