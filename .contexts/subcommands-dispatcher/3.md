## Critical item from letter 2

Restated: the declaration that dispatches `run`, `config { show-dev,
validate }`, `version` does not compile, "because `show_dev` is a copy of
`version`". Reproduced exactly, with the reported message:

```
error: dap.command: levels 'mpy6a config show-dev' and 'mpy6a version' share
a View type; subcommand dispatch would be ambiguous
```

### Root cause: `View` types are structural, not nominal

Letter 1 asserted the opposite ("`@Struct`-generated `View` types are
nominal"), and U2 was confirmed on that false premise. Zig interns struct
types by structure, and that holds for `@Struct` exactly as it does for source
syntax:

```zig
fn mk(comptime tag: []const u8) type {
    _ = tag;
    return struct { inner: u8 };
}
comptime { _ = mk("a") == mk("b"); } // true
```

`View` is `@Struct(.auto, null, &Names, &Types, &Attrs)` over the level's
field list, so two levels whose fields match name for name and type for type
get the _same_ type. Any two flagless leaf levels are therefore one type. In
the reported declaration `run`, `version`, and `config show-dev` all have the
single field `builtin_help: bool`, hence one `View`. This is not an edge case;
it is the common case in real command trees.

`checkCommandNodes` (the U2 guard) converted that ordinary layout into a
compile error, so the landed dispatcher rejected exactly the trees it exists to
serve.

### Why the collision is harmless

A level's commands are exactly its `_`-prefixed `View` fields: declaration
field names may not start with `_`, `Alt` fields keep their declaration name,
and `Spec` names are declaration names, so the `_` set is the `CommandEntry`
set. A `View` type fixes its field names, field order, and field types, hence:

- equal `View` types imply the same command field names (the union tags) in the
  same order, and
- the payload type of each field is part of the `View` type, hence the same
  sub-`View` type.

So any node matching a `View` type has the same tags and the same payload
types: it is dispatch-equivalent. Wire names may differ (a `.name` override),
but dispatch never reads wire names. Two levels can share a `View` while
serving different spellings and different help, and each still dispatches its
own active branch. This is also why removing the guard is sound rather than
merely permissive: there is no tree in which a shared `View` type can select
the wrong union member type.

### Fix (landed)

- `checkCommandNodes` is deleted, along with its call from the shell's `Nodes`
  decl; `Nodes` is now directly `commandNodes(@This())`.
- `NodeOf` keeps matching `NS.View == V`, takes the first match, and still
  rejects a leaf and a foreign value. Because a `View` without `_` command
  fields cannot belong to a level with commands, a leaf match is always
  correct. The leaf message no longer names an arbitrary colliding sibling; it
  now reads `dap.command: a leaf View of '<root>' declares no subcommands`.
- `commandNodes`, `NodeOf`, the `Command` doc block, the `generate` doc block,
  `AGENTS.md`, and `AGENTS-SDK.md` state the structural identity and why it is
  safe, replacing the "distinct `View` type per level" claim.

No parser, `normalize`, `Spec`, `CommandEntry`, ancestor-chain, help, or
`deinit` changes.

### Verification

- New regression tests in M18 (207 tests total, was 204):

- `zig build test`, `zig test src/dap.zig` (207/207), `zig fmt --check`,

  reports the foreign-value message.

## Consequence for U2

U2 asked whether to include a pairwise guard that no two nodes share a `View`
type. The answer was "include it", but the invariant it guarded does not hold
and does not need to. The guard is removed; the mapping is now "first node with
this dispatch shape". If you would rather have per-level identity back, see U4.

## Open questions

- **U4 (non-blocking).** Keep dispatch identity shape-based, or make every level
  nominally unique? Shape-based is landed and needs no API or layout change.
  The alternative is a hidden zero-sized marker field on `View` whose field
  type carries a per-level declaration, which makes `View` types nominally
  distinct again: precise leaf error messages and no reliance on structural
  equivalence, at the cost of one extra public `View` field (field enumerations,
  `deinit` loops, and the `View`-shape tests all have to skip it). Proposal:
  keep shape-based; it is simpler and the equivalence proof is pinned by tests.
  Confirm or override.
