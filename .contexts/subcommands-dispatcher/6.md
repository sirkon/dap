## Critical item from letter 5

**Restated.** On a usage error the help page pointed at the root instead of the subcommand. Running
`zig build run -- config validate` (missing `<path>`) printed `error: field 'path' is invalid or missing` followed by the
root page (`Usage: mpy6a <command> [flags]`), while `config validate -h` printed the correct
`Usage: mpy6a config validate <path> [flags]` page.

### Cause

Failure help was built from the *root namespace's static help data*. `parse` caught every `parseInner` error and called
`printFailureExit`, which rendered `helpTextWithStyle` — root scope, no merge. The successful handoffs that would prove a
subcommand was entered never survived the error: the parent assigned its command field with
`@field(v, c.view_field) = try S.parseInnerHelp(...)`, so on failure nothing was assigned and the root View had no active
chain to merge. `Diag` alone cannot reconstruct the path, which is why the old code documented the page as root-scoped.

### Fix

The partial View now survives the unwinding:

- `parseInnerHelp` takes an `out: *View` and an `errdefer out.* = v;`. Phase 0 (builtin help, `Alt` fields, command
  fields) runs before any fallible step, so the partial View is always safe to walk for help: help reads only the
  `_`-prefixed command fields, never the not-yet-assigned spec fields.
- The handoff stores a failing child's partial View into the parent's command field before rethrowing:

  ```zig
  var sub: S.View = undefined;
  @field(v, c.view_field) = S.parseInnerHelp(allocator, environ, args[i + 1 ..], diag, help_seen, &chain, &sub) catch |err| {
      @field(v, c.view_field) = sub;
      return err;
  };
  ```

- `parse` declares `var failed: View = undefined;` and passes `&failed`; `printFailureExit` now receives that view.
- `contextHelpText` was split into `contextHelpData` (build and fold the scopes) plus a thin renderer; the failure path
  uses `failureHelpText`, which sets `HelpData.error_text` to the diagnostic block and renders the merged page once.
- `parseInner` (the test-facing error-returning entry) is unchanged in signature; it discards the partial View.

The merge machinery is the one `helpRequested`/`usage` already use: one `HelpData` per entered level, folded root-first,
arg groups/commands/name from the deepest scope, builtin help deduped. So the error page and the `-h` page of the same
command are the same page, with the diagnostics prepended.

### Resolution

Both reported cases print the same page now:

```
$ zig build run -- config validate
error: field 'path' is invalid or missing
Usage: mpy6a config validate <path> [flags]

Validate config file.

Arguments:
  <path>    Path to the configuration file.

Flags:
  -h, --help    Show context-sensitive help.
```

`config validate -h` prints the same page without the leading error line. Nothing changes for a failure before any
handoff: a root-level error still renders the unchanged root page.
