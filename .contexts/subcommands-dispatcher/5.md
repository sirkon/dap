## Critical item from letter 4

**Restated.** Context-aware usage looked broken: inside the `.config` branch, `try CLI.usage(cli)` printed the root
usage page instead of the `app config`/`validate` level.

### What the code did on the pinned revision

The pin (`dbdea69`, dap 0.0.11) already renders the config scope from the root view. Reproduced against the reported
declaration, unchanged, with `config` active:

```
$ zig build run -- config
Usage: mpy6a config <command> [flags]

A set of commands to show config, validate config and so on.

Flags:
  -h, --help    Show context-sensitive help.

Commands:
  show-dev    Print the default development configuration file into the stdout and exit.
  validate    Validate config file.

no config subcommand specified
```

`usage` called `contextHelpText(@This(), &v)`; `appendActiveScopes` reads the active `_config` field of that root view
and merges the config scope over the root scope, so the root-view call is context-aware.

### Why the reported page appeared

Neither spelling of the call can produce a root page on 0.0.11:

- `CLI.usage(cli)` prints the config page, as above.
- `CLI.usage(c)` did not compile: `usage` was `fn (v: View)` with the root `View` type, so only the root value was
  accepted. That limitation is what this iteration removes.

The remaining consistent explanation is a stale executable. mpy6a bumped its dap pin from 0.0.9 to 0.0.11 in the same
commit that introduced this dispatch code (`a456410`). Two facts about the older pins were verified:

- **0.0.10 cannot compile this tree at all.** `checkCommandNodes` rejects `mpy6a config show-dev` and `mpy6a version` as
  sharing a `View` type (both are `{ builtin_help: bool }`). This is the collision iteration 3 fixed.
- **0.0.9's `command` is root-typed** (`fn command(view: View)`) and has no `NodeOf`, so the critical snippet does not
  compile against it either.

The `zig-out/bin/mpy6a` that predates the rebuild was therefore built from the old mpy6a CLI, where `config` was not a
subcommand at all (`show_dev_config` was a root command). On that binary `mpy6a config` fails during the scan, and
failure help is root-scoped by design, which is exactly the reported page. `zig build run -- config` on the current pin
prints the config page.

### Resolution

No behaviour change was needed for the root-form call, but the trap that made the sub-view call impossible is gone:
`usage` is now generic over the `View` type, like `command`, and a sub-view renders its own level's merged help. Both
forms were exercised in the real checkout: the branch line was changed to `CLI.usage(c)`, `zig build run -- config`
printed the config page above, and `build.zig.zon` / `src/main.zig` were restored afterwards (mpy6a is clean).

## What landed

### Generic `usage`

```zig
pub fn usage(view: anytype) std.mem.Allocator.Error!void
```

`usage` resolves which level of the tree owns the `View`, starting from the namespace it is called on:

```zig
fn usageChain(comptime NS: type, comptime V: type) ?[]const type {
    comptime {
        @setEvalBranchQuota(1_000_000);
        if (NS.View == V) return &.{NS};
        for (NS.commands) |c| {
            const S = Sub(c.Cmd, subApp(NS.app_meta, c));
            if (usageChain(S, V)) |rest| return &[_]type{NS} ++ rest;
        }
        return null;
    }
}
```

The chain is root-first: the root namespace followed by every command level down to the view's own. `contextHelpText`
now walks that chain instead of assuming its `NS` argument is the root:

- one `HelpData` per chain entry, merged in order;
- then `appendActiveScopes` on the view's own level, so descendants still active in the passed view are included;
- `renderHelpWithStyle` uses the chain's first (outermost) renderer;
- `viewValueType` unwraps pointer layers, so both `usage(v)` and `usage(&v)` work; the parse intercept keeps passing
  `&result`.

Consequences:

- `CLI.usage(cli)` on the root namespace is byte-identical to the previous output (the chain is just the root, and
  active descendants are appended as before).
- `CLI.usage(c)` on a dispatched sub-view now compiles and prints the same merged help: ancestors from the chain plus
  the active descendants of `c`.
- `CLI.usage(leaf)` is legal. Unlike `command`, a leaf has its own scope, so it is not an error.
- A foreign view is `@compileError("dap.usage: argument is not a command View of '<app>'")`, parallel to `command`.
- Calling `usage` on a namespace deeper than the root merges from that namespace down; the root namespace is the form
  that reproduces the parse intercept's full ancestor help.

The `usage` doc comment, `AGENTS.md` (the context-sensitive help bullet), and `AGENTS-SDK.md` (member table plus §10.5)
describe the generic accessor and show the `CLI.usage(c)` branch spelling.
